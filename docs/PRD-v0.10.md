# AI Native Chat — PRD V0.10

修订日期：2026-11-05。主题：手动添加联系人与独立联系人列表。

**状态：待实现的产品需求。当前应用仍为 0.5.0，本文件不代表联系人功能已经上线。**

本版为 [V0.9](PRD-v0.9.md) 的增量修订；未覆盖的聊天、Agent、交付、语音识别和数据要求继续有效。本次新增需求集中列于第 2 节，后续章节使用同一编号细化。应用版本、PRD 版本分别管理。

## 1. 本轮范围与开发基线

### 1.1 范围决定

采用**个人通讯录**：用户主动把另一个账号加入自己的联系人列表。添加立即生效，不要求对方审批，不自动给对方添加联系人。联系人管理负责整理聊天对象，Room 成员关系继续决定聊天数据的访问范围。

保留现有账号注册、登录、Owner 注册开关及注册邀请链接/二维码。取消上一轮讨论中提出的“默认改为邀请制、增加开放/邀请/暂停三种注册模式、重做注册邀请”需求。本轮不开发好友申请/审批、拉黑、陌生人消息箱、联系人分组、联系人备注、个人加好友二维码、跨服务器通讯录或新的群邀请审批。

注册流程唯一关联调整：新账号只初始化自己的 Agent 私聊，停止与全体已有用户自动创建私聊。此项属于联系人与会话初始化修正，不改变注册资格、入口、密码规则、自动登录或邀请有效性。

## 3. 页面与主要流程

### 3.1 独立联系人列表（CT-01）

- 桌面左侧提供“聊天 / 联系人”两个主入口；聊天内原有“聊天 / 已归档”继续作为会话筛选，不与联系人混在同一层。手机提供同级入口，返回键仍按原规则逐层返回。
- 联系人页包含列表搜索、“添加联系人”按钮和联系人列表。搜索只过滤自己的已添加联系人，可按昵称或用户名匹配。
- 列表显示头像、昵称、`@用户名`；按昵称排序，用户名、ID 作为稳定的后续排序键。Agent 使用已有的专用会话入口，不作为人类联系人。
- 空状态：“还没有联系人，按用户名添加一位。”提供添加按钮，不展示全站账号、推荐用户或自动加入的账号。
- 打开联系人显示资料卡：头像、昵称、用户名、“发消息”“移除联系人”。不展示对方的联系人、其他私聊、邀请使用记录或联系方式。

### 3.2 手动添加（CT-02、CT-06）

1. 点击“添加联系人”，输入同一服务器账号的完整用户名。沿用现有用户名规则，忽略首尾空白和大小写，不按昵称进行全站模糊搜索。
2. 点击“查找”，最多返回一个匹配账号的公开资料卡。界面明确区分“查找”和“添加”，查找成功不会保存关系。
3. 点击“添加联系人”，成功后显示“已添加”，进入自己的联系人列表。对方不收到好友申请，也不会被自动加上我；本轮无需审批状态机。
4. 可继续点击“发消息”进入双人聊天；只添加联系人不会生成 Room、消息、未读、推送或 Agent 任务。
5. 已有私聊或群成员资料卡可以直接“添加联系人”，调用同一接口。昵称相同也以稳定 user_id 区分。

| 情况 | 页面与服务端行为 |
| --- | --- |
| 未找到或账号已停用 | 提示“未找到可添加的账号”，不返回全站列表 |
| 输入自己的用户名 | 提示“不能添加自己” |
| 已是联系人 / 连点 / 两个设备同时添加 | 返回同一联系人，不重复记录；按钮显示“已添加” |
| 尝试添加 Agent | 使用专用 Agent 入口，不建立人类联系人关系 |
| 网络中断 | 保留输入，可重试；请求结果以服务端为准 |

查找仅限已登录用户，不提供游客搜索。建议每账号每分钟最多 20 次查找，超限返回可重试提示；计数应支持重启后的合理恢复，不影响已有联系人列表的读取。

### 3.3 发消息与移除（CT-03、CT-05）

- 从联系人点击“发消息”：复用双方已有的双人 Room；没有则创建一个，沿用唯一 `dm_key` 防止重复。Agent 默认加入和历史策略沿用 V0.9。
- 新建私聊只选择一个联系人；新建群聊选择多个联系人并填写群名。选择器可搜索自己的联系人，不默认展示同服务器全部账号。
- 通讯录是单向的：A 添加 B 后，A 可以发起聊天，B 可以在该会话中正常回复，即使 B 尚未添加 A；B 可在资料卡手动添加 A。
- B 收到一条真实消息时，该聊天正常进入 B 的会话列表，但不会进入 B 的联系人列表。聊天对象与联系人列表允许不同，界面不能把收到消息解释为自动添加联系人。
- 为避免新的空会话干扰，首次打开无消息的双人聊天只在主动打开者一侧显示；对方在首条实际消息提交后再收到会话更新和未读。若已存在有内容的 Room，则按原会话状态显示。
- 移除联系人前提示“仅从你的联系人列表移除，聊天记录保留”。仅删除本人到对方的关系，不删除对方列表、历史消息、文件、记忆或群成员资格，不推送系统聊天消息。
- 移除后，原有私聊仍可打开和继续对话；本轮没有拉黑或禁止陌生人消息的含义。可以重新手动添加，仍复用原 Room。
- 联系人修改同步到本人其他登录设备。联系人昵称/头像使用当前账号资料；本人列表不复制一份永久昵称快照。

### 3.4 群聊与现有邀请（CT-05、CT-06）

- 新建群聊、手动加群成员时，候选为操作者的联系人；已有群成员仍可查看群内全部当前成员，不要求彼此都是联系人。
- 群中“添加联系人”只建立本人通讯录关系，不移出群、不扩大旧历史可见范围；从群成员资料卡发起新私聊前先添加为联系人。
- 注册邀请和既有群邀请链接继续可用。成功注册/入群不会自动添加邀请人或其他群成员为联系人。
- 既有链接中包含注册和进群的行为、次数限制、撤销及历史起点沿用 V0.9。本版不重做邀请资格或群管理角色。
- “设置 → 成员”继续是 Owner/获授权成员的账号管理入口，名称使用“服务器成员管理”，与普通用户的“联系人”页区分；其创建账号权限不等于替别人维护通讯录。

## 4. 账号初始化与数据兼容

### 4.1 停止全员自动创建（CT-04）

- 收敛统一初始化函数：注册、邀请兑换后注册、Owner/获授权成员建号及 CLI 建号调用相同逻辑，只保证个人 Agent 私聊存在。
- 新账号联系人列表为空，普通双人私聊为空；若通过已有有效群邀请加入群，则该群正常显示。
- 服务启动、重连、用户列表刷新、注册事件不能补建全员私聊或自动导入联系人。
- 公开注册开关的现有默认值与保存值不变。本轮不增加邮箱/手机验证、找回密码流程或新注册模式；管理员直接建号也不使新账号自动成为管理员联系人。

### 4.2 升级迁移（CT-08）

1. 升级前按原流程备份，新增联系人表及必要的会话可见性字段；不删除账号、Room 或历史内容。
2. 所有已有用户从空联系人列表开始。已有私聊数量不能当作手动添加的证据；群成员、邀请人也不自动导入。
3. 已有有内容的双人私聊继续显示并可访问，资料卡提供添加联系人入口。已有群聊和 Agent 私聊保持原状态。
4. 对没有任何消息记录、交付物或任务记录的旧双人私聊，逐用户设为归档，保留 Room 和 `dm_key`，不做永久删除。包含已删除消息痕迹的 Room 也不作为纯空会话处理。
5. 空私聊仍可在“已归档”找到；后续主动打开或收到真实消息时按既有规则恢复。不要在每次启动时重复执行空私聊归档，避免覆盖用户后来的选择。
6. 迁移提供仅检查的预览输出和执行计数；记录迁移版本，事务执行且重复运行幂等。旧邀请、账号权限、语音转写、Agent 设置及工作目录不受影响。

## 5. 服务端契约与实现边界（CT-07、CT-09）

### 5.1 最小数据关系

| 对象 | 至少保存 | 约束 |
| --- | --- | --- |
| Contact | owner_user_id、contact_user_id、created_at | 组合主键；不能指向本人、Agent 或停用账号；无双向自动写入 |
| 无消息双人 Room 的个人显示状态 | room_id、user_id、是否主动打开过 | 复用成员关系或增加最小字段；首条消息前不展示给未主动打开的一方 |
| 迁移记录 | 版本、执行时间、影响数量 | 一次执行；可预览；重复执行不反复归档 |

普通联系人移除使用删除关系即可，不引入好友申请、同意、拒绝、过期等状态。目标账号停用后，关系可保留，列表标记“账号已停用”，禁止创建新聊天和新邀请；既有消息按原权限继续读取。以上停用限制同样在服务端校验。

### 5.2 建议 API

具体路径可随实现调整，行为须满足下列契约：

| 接口 | 用途与要求 |
| --- | --- |
| `GET /api/contacts` | 只返回当前登录用户的联系人；返回最小公开资料，不接受任意 owner_id |
| `GET /api/users/lookup?username=...` | 已登录、精确用户名查找；最多一个结果，限制频率 |
| `POST /api/contacts`，`{user_id}` | 校验目标并幂等添加到当前用户列表，不建聊天、不向对方写关系 |
| `DELETE /api/contacts/{user_id}` | 幂等移除本人的关系，不清理聊天或对方关系 |
| `GET /api/admin/users` | 既有账号管理权限检查后返回服务器成员目录；管理员专用 |
| 既有创建私聊/群聊/加成员接口 | 新会话的目标、手动加入的目标须为操作者联系人；已建立会话中的回复仍按 Room 权限 |

现有 `GET /api/users` 不得继续为所有普通用户返回全站账号。升级前查清其全部调用方：联系人选择器改用联系人接口，账号管理改用管理员接口，已有会话的头像、作者名和 @ 选择使用该会话有权查看的成员资料。过渡保留旧路径时也必须收敛范围，不能只隐藏前端。

### 5.3 权限、同步与 Agent

- 联系人的增删和读取必须由登录身份确定归属，禁止通过参数修改他人通讯录；管理员账号管理能力也不自动授予代改通讯录能力。
- 添加关系不授予 Room 成员资格、不开放对方其他会话、联系人或历史消息。联系人、会话成员、账号管理三种权限分别检查。
- 通过 WebSocket 向本人所有设备发送联系人增删/资料变化事件；断线重连重新拉取列表。事件不广播全站，不产生对方未读提醒。
- 联系人变动不触发 Agent 发言、记忆整理、语音识别或外部操作。Agent 读当前 Room 成员仍按原范围，不把完整人类通讯录注入每次模型上下文。
- 本轮不新增 Agent 自动添加联系人或管理通讯录的专用工具；V0.8 的终端执行权限维持原约定。应用层联系人校验不承诺操作系统级隔离。
- 联系人关系随完整备份恢复。按 Room 导出不附带当前用户其他联系人；账号停用/恢复、删除策略沿用原系统规则。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| AC-01 | 公开注册、邀请注册、网页建号、CLI 建号 | 仅创建个人 Agent 私聊；联系人为空；现有其他成员列表不新增空私聊 |
| AC-02 | A 精确查找并添加 B | 只在 A 通讯录显示 B；B 不被自动互加；不产生 Room、消息、任务或未读 |
| AC-03 | 昵称重复、用户名大小写、自身/停用/Agent 账号 | 定位稳定 ID；错误明确；查找不返回全站目录 |

| AC-05 | A 首次打开 B 的聊天，随后发送消息 | 打开阶段只向 A 显示；发送后 B 正常收信和回复；B 通讯录仍不含 A |
| AC-06 | A 移除 B 后打开旧私聊，再次添加 | 历史、文件和群关系保留；原私聊可继续；重新添加复用 Room |
| AC-07 | 新建群、群内查看成员、群邀请注册/入群 | 普通选择器仅列本人联系人；群成员可查看；进群不自动互加联系人 |
| AC-08 | 直接请求旧目录接口、伪造 owner_id/user_id | 普通用户不能取得全站目录或修改他人关系；管理员仍可管理账号 |
| AC-09 | 多设备添加/移除、断线重连、对方改头像/昵称 | 本人各端及时同步、旧显示可恢复，不向其他用户泄漏通讯录 |
| AC-10 | 旧库升级、预览、重复迁移、备份恢复 | 有内容会话保留、纯空私聊仅归档、联系人不自动导入、迁移幂等 |
| AC-11 | 注册开关开/关、有效/过期/撤销/耗尽邀请 | 保持现有注册和邀请规则，没有新注册模式或默认值变更 |
| AC-12 | 原聊天、@、Agent、语音、交付卡及取消/重试 | 原功能回归通过；不存在联系人变动引发的模型调用 |

桌面和手机均检查添加、空列表、列表搜索、发消息、移除和返回导航。接口测试必须覆盖直接调用，不能只以按钮隐藏作为权限通过证据。实际开发完成后把验收结果补入测试文档，本 PRD 不预填通过结论。

## 7. 实施顺序

1. **基础与初始化**：联系人数据/接口、统一账号初始化、精确查找和归属校验。
2. **页面与选择器**：独立联系人列表、资料卡添加/移除、私聊/群聊候选收敛、首次私聊显示规则。
3. **兼容与收尾**：旧目录调用改造、旧空私聊归档迁移、本人多设备同步、备份及完整回归。

三步作为同一版交付：只有取消全员自动私聊、联系人页、候选数据范围和旧数据兼容同时完成，才可标记联系人功能已实现。当前阶段仅完成需求设计和基线核对。
